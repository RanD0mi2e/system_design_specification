# 需求文档：离线服务系统 (Offline Service)

## 需求概述

基于现有的 `probeNetworkQuality()` 网络探测函数，构建一套完整的从网络质量检测到离线服务的业务系统。系统需要在移动端（企业微信/微信 H5）网络不稳定或完全离线的场景下，保障用户能够继续完成巡视、作业等关键业务操作，并在网络恢复后自动同步数据到服务端。

---

## 功能需求

### FR-1: 网络状态监控

#### FR-1.1: 自适应网络探测
- 系统应在应用启动时自动开始网络质量探测
- 网络良好时，探测间隔为 30 秒
- 网络较差时，探测间隔缩短为 10 秒
- 完全离线时，探测间隔为 5 秒（等待恢复）
- 探测超时阈值为 1000ms

#### FR-1.2: 网络状态分级
- 系统应将网络状态分为三个等级：`good`（良好）、`weak`（较差）、`offline`（离线）
- 单次探测失败标记为 `weak`
- 连续 3 次探测失败标记为 `offline`
- 探测成功且响应时间 < 1000ms 标记为 `good`

#### FR-1.3: 浏览器事件监听
- 系统应监听浏览器 `online` / `offline` 事件作为快速响应通道
- 收到 `online` 事件时立即触发一次主动探测
- 收到 `offline` 事件时立即将状态标记为 `offline`

#### FR-1.4: 状态变化通知
- 网络状态发生变化时，系统应通知所有已注册的监听者
- 状态变化事件应包含：新状态、上次探测时间、探测耗时

---

### FR-2: 离线策略管理

#### FR-2.1: 三级策略模式
- **在线模式 (online)**：所有操作正常走网络请求，写操作同时缓存到本地
- **谨慎模式 (cautious)**：读操作走网络（带缓存兜底），写操作本地优先并加入同步队列，上传操作暂停
- **离线模式 (offline)**：所有操作仅走本地存储，写操作全部加入同步队列

#### FR-2.2: 策略自动切换
- 网络状态变为 `good` 时自动切换到在线模式
- 网络状态变为 `weak` 时自动切换到谨慎模式
- 网络状态变为 `offline` 时自动切换到离线模式

#### FR-2.3: 操作类型策略
- 系统应针对四种操作类型（read / write / upload / download）提供差异化策略
- 每种策略应包含：是否允许网络请求、是否需要本地缓存、是否加入同步队列、重试配置、超时配置

---

### FR-3: 本地数据持久化

#### FR-3.1: 同步任务持久化
- 所有离线操作产生的同步任务必须持久化到 IndexedDB
- 同步任务应包含：唯一 ID、业务类型、业务 ID、操作类型、状态、优先级、载荷数据、创建时间、重试次数
- 任务状态包括：`pending`、`syncing`、`success`、`failed`、`conflict`

#### FR-3.2: 数据不丢失保证
- 用户的任何写操作数据，无论网络状态如何，必须至少存在于本地 IndexedDB 或已同步到服务端
- 应用意外关闭后重新打开，未同步的数据必须仍然存在

#### FR-3.3: 存储空间管理
- 系统应监控 IndexedDB 存储使用情况
- 存储空间不足时，自动清理已完成的同步任务和过期的网络快照
- 清理后仍不足时，通知用户手动处理

---

### FR-4: 数据同步引擎

#### FR-4.1: 自动同步触发
- 网络从非 `good` 状态恢复到 `good` 时，自动开始同步待处理任务
- 同步过程中网络再次断开时，立即停止同步

#### FR-4.2: 优先级排序
- 同步任务按优先级（数字越小越高）排序执行
- 同优先级的任务按创建时间先后顺序执行

#### FR-4.3: 重试机制
- 同步失败的任务自动重试，重试次数不超过配置的最大值
- 重试采用指数退避策略
- 超过最大重试次数的任务标记为 `failed`

#### FR-4.4: 批量同步
- 单次同步批次最多处理 50 个任务
- 批量同步完成后触发完成事件，包含成功/失败/冲突数量统计

#### FR-4.5: 手动同步
- 用户可以手动触发同步操作
- 用户可以重试所有失败的任务

---

### FR-5: 冲突解决

#### FR-5.1: 冲突检测
- 同步提交时如果服务端返回 409 状态码，识别为数据冲突
- 检测到冲突后获取服务端最新数据

#### FR-5.2: 冲突解决策略
- 支持四种策略：本地优先 (local-first)、远程优先 (remote-first)、合并 (merge)、用户决定 (manual)
- 默认策略为本地优先（保护用户离线期间的操作）
- 不同业务类型可配置不同的默认策略

#### FR-5.3: 手动冲突解决
- 当策略为 `manual` 时，向用户展示本地版本和远程版本的差异
- 用户选择后按选择结果提交

---

### FR-6: 用户界面

#### FR-6.1: 网络状态指示器
- 当网络状态不为 `good` 时，在页面顶部显示通知栏
- 弱网时显示黄色提示："网络不稳定，数据将自动保存到本地"
- 离线时显示红色提示："当前离线，数据已保存到本地，联网后自动同步"

#### FR-6.2: 同步进度展示
- 显示待同步任务数量（Badge 角标）
- 同步进行中时显示进度信息
- 同步完成时显示 Toast 提示结果

#### FR-6.3: 同步管理面板（可选）
- 用户可查看所有待同步、失败的任务列表
- 用户可手动重试失败任务或删除任务

---

## 非功能需求

### NFR-1: 性能
- 网络探测请求应使用小体积资源（< 2KB），避免占用带宽
- 同步操作不应阻塞 UI 主线程
- IndexedDB 批量操作应使用事务，减少 I/O 开销

### NFR-2: 可靠性
- 系统应保证数据零丢失（在 IndexedDB 可用的前提下）
- 同步引擎应具备断点续传能力（中断后从未完成处继续）
- 应用崩溃或意外关闭不影响已持久化的同步队列

### NFR-3: 兼容性
- 支持企业微信内置浏览器（iOS / Android）
- 支持微信内置浏览器
- 支持主流移动端浏览器（Chrome Mobile、Safari Mobile）
- IndexedDB 不可用时降级到 localStorage

### NFR-4: 安全性
- 同步请求复用现有 JWT Token 认证机制
- 不同用户的离线数据应隔离存储
- Token 过期时暂停同步并触发重新认证

### NFR-5: 可观测性
- 关键操作（状态切换、同步开始/完成/失败）应输出 console 日志
- 网络状态历史应记录到 IndexedDB 供分析

## 验收标准

### AC-1: 网络监控验收
- [ ] AC-1.1: 应用启动后 1 秒内完成首次网络探测并确定初始状态
- [ ] AC-1.2: 网络断开后 5 秒内状态变为 `offline`
- [ ] AC-1.3: 网络恢复后 10 秒内状态变为 `good`（取决于探测间隔）
- [ ] AC-1.4: 探测间隔根据网络状态自适应调整

### AC-2: 离线操作验收
- [ ] AC-2.1: 离线状态下用户提交巡视数据，数据成功保存到 IndexedDB
- [ ] AC-2.2: 离线状态下用户提交作业数据，数据成功保存到 IndexedDB
- [ ] AC-2.3: 离线状态下不发起任何网络请求
- [ ] AC-2.4: 弱网状态下写操作失败后自动降级到本地存储

### AC-3: 数据同步验收
- [ ] AC-3.1: 网络恢复后自动开始同步离线数据
- [ ] AC-3.2: 同步按优先级顺序执行
- [ ] AC-3.3: 同步失败的任务自动重试（不超过最大次数）
- [ ] AC-3.4: 所有任务同步完成后显示结果通知
- [ ] AC-3.5: 同步过程中网络再次断开，正确暂停并保留未同步任务

### AC-4: 冲突处理验收
- [ ] AC-4.1: 服务端返回 409 时正确识别为冲突
- [ ] AC-4.2: 本地优先策略下使用本地数据覆盖远程
- [ ] AC-4.3: 远程优先策略下使用远程数据更新本地

### AC-5: UI 反馈验收
- [ ] AC-5.1: 离线时页面顶部显示红色通知栏
- [ ] AC-5.2: 弱网时页面顶部显示黄色通知栏
- [ ] AC-5.3: 网络恢复后通知栏自动消失
- [ ] AC-5.4: 待同步任务数量以 Badge 形式展示

### AC-6: 数据完整性验收
- [ ] AC-6.1: 任何网络状态下用户操作数据不丢失
- [ ] AC-6.2: 应用意外关闭后重新打开，未同步数据仍存在
- [ ] AC-6.3: 同步成功的数据从本地队列中正确清除
